# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

**Team Trip Planner**: an MVP for small groups (~10–15 people) to agree on travel dates, plan a day-by-day itinerary, split costs, and keep trip photos on Google Drive. The UI and all user-facing messages (including backend error `detail`) are in **Vietnamese**.

**Read first:**
- `AGENT_RULE.md`: mandatory workflow and coding rules. Read the SDD → backend first (migration → Entity → Repository → DTO record → Service → Controller + Swagger) → frontend types copied 1:1 from the Java DTOs → both builds green before reporting.
- `docs/sdd-phase-N.md`: the design for each phase. It is the contract. If it conflicts with the code or with `AGENT_RULE.md`, ask the user before coding.
- `/run-phase N` (`.claude/commands/run-phase.md`) runs a phase end to end.

The two Vietnamese spec files at the root are the original product specs. The plan was later changed to **5 phases**:
1. Auth + trips + invites + countdown
2. Day-level availability + lock dates
3. Itinerary (drag & drop, auto-insert by time) + dress code + checklist (deployment moved to phase 5; `backend/Dockerfile` is ready but not yet built)
4. Polls + expense split with VietQR
5. Drive album links + room assignment + share previews (production deploy postponed)

Login is Google **or** username/password. No Drive OAuth scope is requested, so the album (phase 5) only stores Drive links. Trip covers, avatars and dress-code sample images can also be **uploaded from the device into MinIO** (`docs/sdd-media-upload.md`).

## Current state

All 5 phases, the MinIO image upload and the proposals wishlist are implemented (see `docs/sdd-phase-{1..5}.md`, `docs/sdd-media-upload.md` and `docs/sdd-proposals.md`). **Email notifications** (`docs/sdd-email-notifications.md`) are being built in 3 phases: **All three phases are done**: N1 (infrastructure), N2 (member/expense/settlement events + per-trip mute) and N3 (countdown emails). The backend runs against local MySQL 8.0.44 and MinIO, and all tests pass (194 at the end of N3, 1 skipped without real MinIO), including the integration tests. Gmail SMTP login with the local App Password works, but no notification email has been checked end to end in a real inbox or browser yet. **Production:** `docker-compose.prod.yml` + `.env.prod` (template `.env.prod.example`) runs frontend, backend, MySQL and MinIO behind the **host's own nginx** (all ports bound to 127.0.0.1; nginx sends `/api/` and `/share/` to :8080, `/trip-planner/` to :9000, the rest to :3000). Run `docker compose -f docker-compose.prod.yml --env-file .env.prod up -d --build`. Backend env vars use the exact names `application.yml` reads (`DB_URL`, `JWT_SECRET`, `MAIL_*`, `PUBLIC_BASE_URL`…). Both images build and the stack was smoke-tested locally (migrations V1–V9, health UP, frontend 200); `deploy/Caddyfile` is no longer used.

## Architecture

**Backend** (`com.tripplanner`). Packages are split by feature (`auth`, `user`, `trip`) plus `common` and `config`.
- **Auth:** stateless. The app issues its own HS256 JWT (`JwtService`), and `oauth2-resource-server` verifies it. The JWT `sub` claim is the userId; controllers read it with `@AuthenticationPrincipal Jwt` + `CurrentUser.id(jwt)`. Access tokens live **15 minutes** (`JWT_ACCESS_TTL_MINUTES`).
- **Refresh tokens (V8, `docs/sdd-refresh-token.md`, package `auth.refresh`):** login/register/google open a **token family** and set the HttpOnly cookie `tp_rt` (`Path=/api/v1/auth`, `SameSite=Strict`, `Secure`). `POST /auth/refresh` rotates the token: the old one is consumed, and a new one is issued in the same family. The decision lives in the pure class `RefreshTokenPolicy` (unit-tested): a consumed token reused within 10 s is `REFRESH_TOKEN_STALE` (two tabs refreshing at once, no revoke); later reuse is `REFRESH_TOKEN_REUSED`, which **revokes the whole family**. `rotate` locks the family row and uses `noRollbackFor = BusinessException` so the revoke commits. Only SHA-256 hashes are stored; `user_id` sits on the family only (BCNF); there is no self-FK `parent_id` (MySQL cascade depth 15). `POST /auth/logout` (cookie) and `/auth/logout-all` (access token) revoke families; a nightly `@Scheduled` job deletes old families. CORS has `allowCredentials(true)`.
- **Google login:** the FE sends a Google ID token to `POST /api/v1/auth/google`. `NimbusGoogleTokenVerifier` checks it against Google's JWKS. That decoder is deliberately **not** a bean, so it never clashes with the app's `JwtDecoder`. Tests mock the `GoogleTokenVerifier` interface. A password account can attach Google from the profile (`PUT/DELETE /api/v1/users/me/google`, `UserService.linkGoogle/unlinkGoogle`, `GoogleLinkSection`); two existing accounts are never merged automatically. Unlinking also clears `email`, otherwise the next Google login would relink by email. The Google button is hidden while `VITE_GOOGLE_CLIENT_ID` is empty, and the backend returns `GOOGLE_LOGIN_NOT_CONFIGURED` while `GOOGLE_CLIENT_ID` is empty; both must hold the same Client ID.
- **Authorization:** every trip-scoped check goes through `TripAccessService.require(tripId, userId, minRole)`, where `VIEWER < EDITOR < OWNER` by enum order. Reuse it for later phases (availability, itinerary, …).
- **Errors:** `BusinessException(ErrorCode)` → `GlobalExceptionHandler` → `ProblemDetail` with extra `code` and optional `fieldErrors`. 401/403 raised by the security filter chain use the same shape. To add an error, add it to `ErrorCode` **and** to `frontend/src/types/api.ts`.
- **Media (MinIO/S3):** `POST /api/v1/media` (multipart `file` + `purpose`) checks the image type by **magic bytes** (`ImageType`), stores it under `{purpose}/{yyyy}/{MM}/{uuid}.{ext}` through the `StorageService` interface (`MinioStorageService`), and records metadata in `media_files`. It returns a public URL, which the FE writes into the existing URL fields; nothing else references `media_files`. URLs are **computed** from `MINIO_PUBLIC_URL` + bucket + key and never stored there. Tests mock `StorageService`. The MinIO SDK 8.x needs `okhttp-jvm` declared explicitly in the pom, because the OkHttp 5 `okhttp` artifact is an empty jar for Maven.
- **Time:** times are stored in UTC (`hibernate.jdbc.time_zone=UTC`). "Today" comes from the injected `Clock` (Asia/Ho_Chi_Minh). Trip status (`TripStatus`) is **computed** from `start_date`/`end_date`, never stored.

**Schema rules (MySQL 8, Flyway, `ddl-auto=validate`):**
- Never edit an existing migration. Add `V{n+1}__*.sql` instead.
- `trip_members` has a composite PK (`@EmbeddedId TripMemberId` + `@MapsId`) and implements `Persistable`, so `save()` persists instead of merging.
- "Exactly one OWNER per trip" is enforced by the generated column `owner_trip_id` with a UNIQUE index. That column is intentionally unmapped. Ownership transfer demotes the current owner and flushes **before** promoting the new one.
- MySQL rejects `ON DELETE CASCADE`/`SET NULL` on a foreign key whose column feeds a generated column (error 1215). So `fk_trip_members_trip` has no cascade, and the app deletes members before deleting a trip.
- MySQL DDL is not transactional. If a migration fails halfway, the tables it already created stay behind and Flyway records the migration with `success=0`. Drop those leftovers and that history row (or run `flyway repair`) before retrying.
- Enum columns are `VARCHAR` and need `@JdbcTypeCode(SqlTypes.VARCHAR)`. Otherwise Hibernate expects a MySQL `ENUM` and validation fails.
- `member_availabilities` (V2) has a natural PK `(trip_id, user_id, avail_date)` and a composite FK `(trip_id, user_id)` → `trip_members` with `ON DELETE CASCADE`, so removing a member also removes their availability. A missing row means "not answered yet".
- **Locked** means `trips.start_date IS NOT NULL`; there is no flag column. Since V3, `trip_days` is a persistent "Day N" with **no stored date**. Its date is derived as `start_date + day_index - 1` (`TripDay.dateIn`). Unlocking keeps the days and everything in them. Locking N days creates missing days 1..N and deletes days with index > N only if they are empty; days that still have content become **overflow** days. `TripDayService` is the only writer of `start_date`/`end_date` and of day creation/deletion during lock (`ItineraryService.deleteOverflowDay` can delete overflow days).
- The suggestion algorithm lives in `AvailabilitySuggester`, a pure class with its own unit test. Scoring: AVAILABLE = 2, MAYBE = 1, BUSY or unanswered = 0. It returns the top 3 non-overlapping windows, considering only days from today onward.
- `TINYINT`/`SMALLINT` columns are mapped as `Integer` with `columnDefinition`, so `ddl-auto=validate` accepts them.
- `itinerary_items` references only `trip_day_id` (no `trip_id`). To check permissions on a child resource, look up its trip id through a JPQL projection (`findTripIdByDayId`, `findTripIdByItemId`, …), then call `TripAccessService`. Ordering uses `ItineraryOrdering` (pure, unit-tested): an item with a time goes before the first item with a later time, otherwise last; an item without a time goes last when added and keeps its slot when edited. `sort_order` has no UNIQUE constraint and is renumbered 0..n-1 after every write. Moving an item to another day uses `POST /itinerary-items/{id}/move`.
- Tables with their own `trip_id` that reference a member (`trip_checklists.assignee_id`, `expenses.paid_by`, `settlements.from_user/to_user`) use a composite FK `(trip_id, user_id)` → `trip_members` with **no cascade**. Child tables **without** `trip_id` (`expense_shares`, `poll_votes`) do not store it, because that would be a transitive dependency; their "must be a member" rule is checked in the service.
- `TripService.delete` deletes, in order: settlements → expenses (shares cascade) → checklist → members → trip. Polls, options, votes and days cascade from the trip. `TripMemberService.removeMembership` returns `MEMBER_HAS_EXPENSES` (409) if the member has paid or owes anything, or has settlements; otherwise it deletes their poll votes and unassigns their checklist items. When you add a table that references members, update both places.
- **Album & rooms (phase 5):** the album stores only `drive_file_id`. View and thumbnail URLs are derived by `DriveLinks`, a pure class that parses file and folder links. Day tags live in a separate table, `album_photo_days`, to stay in BCNF. `room_assignments` is `(room_id, user_id)` with no `trip_id`, so `RoomService` enforces "at most one room per member per trip", capacity limits and membership. Removing a member deletes their room assignment but keeps the photos they added.
- **Proposals wishlist (V7):** `trip_proposals` + `proposal_votes` (no `trip_id`, like `poll_votes`). "Scheduled" means `itinerary_item_id IS NOT NULL` (UNIQUE, `ON DELETE SET NULL`), so deleting the itinerary item returns the proposal to the wishlist; vote counts are never stored. Add/vote: any member; edit/delete: creator or OWNER; `POST /proposals/{id}/schedule`: EDITOR+ on a locked trip, non-overflow day. It row-locks the proposal (`PESSIMISTIC_WRITE`) and calls `ItineraryService.createItem` in the same transaction (only `mapsUrl` and `note` are copied, not `referenceUrl`). The FE shows it in the "Ý tưởng" tab (`IdeasTab`: Wishlist / Bình chọn, tab value still `polls`).
- **Email notifications (`docs/sdd-email-notifications.md`, package `notification`, V9):** Transactional Outbox + Spring `@Scheduled` (no JobRunr/Quartz). One `notifications` row = one event for one recipient (`payload` JSON is a snapshot; `category`/`channel` derive from `NotificationType`, not stored). `NotificationOutbox` is the only writer (JdbcTemplate, `INSERT IGNORE` on `dedup_key`, **swallows and logs every error** so a notification bug never breaks the business action). `NotificationDispatcher.runOnce()` (every 10 s, `NOTIFY_DISPATCH_INTERVAL_MS`) releases `SENDING` rows stuck >10 min, enforces the daily limit, claims due groups `(user, trip, channel)` with `FOR UPDATE SKIP LOCKED` (a group is due when its earliest `send_after` passes; all its PENDING rows go in one email), re-checks email/prefs/mute, keeps the newest row per `coalesce_key`, sends, and retries with `RetryPolicy` (1/5/15/60 min, FAILED after 5). JDBC timestamps go through `Db.utc` (UTC `LocalDateTime`) to match Hibernate. Jobs are skipped when `app.notifications.scheduler-enabled=false` (test profile); tests call `runOnce()` and mock `MailGateway`. The config key is `app.notifications` because `notify` clashes with `Object.notify()` in the record.
  - `users.notify_email` holds only a **verified** address and is separate from `users.email` (the Google login email used for auto-linking). Google sign-up/link fills it; unlinking Google keeps it. Password accounts verify via `email_verifications` (SHA-256 token, 24 h, 60 s cooldown, 5/day). Verification and test mails are sent **synchronously**, not via the outbox, so raw tokens never sit in the DB.
  - Prefs live in `user_notification_prefs` (no row = all on); per-trip mute in `trip_notification_mutes` (composite FK → `trip_members` ON DELETE CASCADE). `notifications` cascades from `users` and `trips`, so `TripService.delete`/`removeMembership` need no changes for these tables.
  - Unsubscribe tokens (`UnsubscribeTokens`) are HMAC with a key derived from `JWT_SECRET`, deliberately **not** JWTs (the resource server would accept a JWT as an access token). Emails carry `List-Unsubscribe` + one-click (RFC 8058) pointing at `PUBLIC_BASE_URL`; footer links go to the FE `/unsubscribe` page, which requires a click (link scanners must not unsubscribe people). `/verify-email` and `/unsubscribe` are public FE routes; the matching `/api/v1/notifications/*` endpoints are permitted in `SecurityConfig`.
  - **Events (N2):** `TripService.join`, `TripMemberService.removeMember`, `ExpenseService` (create/update/delete) and `SettlementService` publish records from `notification.event`; `NotificationEventListener` (`@TransactionalEventListener(BEFORE_COMMIT)`) turns them into outbox rows. It reads only through JDBC (`NotificationAudience`) and swallows every error, because a failing JPA repository call would mark the business transaction rollback-only. Hibernate may not have flushed yet at BEFORE_COMMIT, so the listener always excludes the subject by id. Rows are due immediately by default (`NOTIFY_DELAY_MINUTES=0`, user's choice: email right away); a positive delay brings back batching of several events per trip into one email. Expense edits/deletes inside the waiting window update or cancel the PENDING row by `coalesce_key` (`EXP:{id}`, `STL:{id}`) following the pure `CoalescePlanner`; people who were never told get no "deleted" email. Recipients without a verified email, with the category off or with the trip muted get no row. A new domain action that should email people needs an event + a listener method.
  - **Countdown (N3, `notification.countdown`):** `CountdownJob` runs on `app.notifications.countdown-cron` (08:00 VN) and once at startup if today's run time has passed; for trips whose `start_date` is today + one of `countdown-days` it enqueues one `COUNTDOWN` row per eligible member with `dedup_key = CD:{trip}:{user}:{start_date}:{daysLeft}` (re-runs are no-ops, re-locking to a new date counts again). `CountdownContentBuilder` snapshots day 1 (itinerary, dress code) and the recipient's unchecked checklist items into the payload. Email dress-code swatches use `mail/DressColorStyles`, which must stay in sync with `lib/dressColors.ts`; preset cover colours come from `CoverImageRenderer.presetHexColors`. Comments in mail templates must be `<!--/* */-->` or they leak into the email.
  - Per-trip mute: `GET/PUT /api/v1/trips/{tripId}/notification-mute` (VIEWER+); muting cancels the caller's PENDING rows for that trip. The trip page "⋯" menu is shown to every member for this. `TripDetailPage` tabs are driven by `?tab=` so email links open the right tab.
  - Emails are rendered by core Thymeleaf (`MailRenderer`, templates in `src/main/resources/mail/`, not the MVC starter): body first, then `layout.html`/`.txt`. Call record accessors as `${x.name()}` in templates (OGNL doesn't treat them as getters).
- **Share preview:** `share/SharePageController` (public `/share/**`, permitted in `SecurityConfig`) serves Open Graph HTML plus `cover.png`. `CoverImageRenderer` draws preset gradients with Java2D (no text) using the same colours as `lib/covers.ts`, so keep both in sync. Previews only work once the backend is publicly reachable. The reverse proxy must send `/share/` to the backend, like `/api/` (production currently uses the host's own nginx, not `deploy/Caddyfile`). If it doesn't, the SPA route `/share/:code/*` (`ShareRedirectPage`) redirects to `/join/:code`, so joining still works but link previews don't.
- **Money (phase 4):** amounts are VND as `long`. `ExpenseSplitter` gives the remainder of an equal split to the payer. `BalanceCalculator` uses net = paid − share + sent − received and counts only CONFIRMED settlements; suggested transfers come from a greedy match (at most N−1 transfers). Both classes are pure and unit-tested. Invariant: the sum of `expense_shares` equals `expenses.amount`. **Permissions:** only the creator, the payer or the OWNER can edit or delete an expense, and only the OWNER can record an expense paid by someone else. Plain EDITORs cannot, because everyone who joins through an invite link is an EDITOR by default.
- Bank accounts live on `users` (`bank_bin`/`bank_account_no`/`bank_account_name`: all three set or all three null). The bank name is derived from the BIN through `BankDirectory`. The VietQR payload (EMVCo + CRC16) is built **on the client** in `lib/vietqr.ts` and drawn with `qrcode`; account numbers are never sent to a third-party service.
- Dress code colours live in `trip_day_dress_colors` and must use a key from a fixed palette that is kept in sync between `TripDayDressColor.PALETTE` (BE) and `lib/dressColors.ts` (FE); the hex values and labels are also copied in `notification/mail/DressColorStyles` for emails.
- Itinerary and checklist write endpoints return the **whole** resource (`ItineraryResponse` / `ChecklistResponse`), and the FE writes it straight into the cache.

**Frontend** (`src/`):
- `types/`: mirrors the Java DTOs 1:1.
- `api/`: axios calls only (`withCredentials: true` for the refresh cookie). The `lib/api.ts` interceptor attaches the JWT. On a 401 from a non-`/auth/*` call it runs `refreshSession()` once and retries the request; if that fails it fires `UNAUTHORIZED_EVENT` (detail = error code) for `AuthProvider`.
- Access token is **memory-only** (`lib/token.ts`), never localStorage; `tp.hasSession` is a non-secret hint so that anonymous visitors skip the refresh call. `lib/session.ts` makes refresh single-flight inside a tab and serialises it across tabs with Web Locks, retrying once on `REFRESH_TOKEN_STALE`. On page load `AuthProvider` calls refresh to restore the session. `BroadcastChannel('tp-auth')` syncs login/logout across tabs. Profile → Bảo mật has "Đăng xuất mọi thiết bị". Profile also has `NotificationSection` (notify email + verification, category switches, "Gửi mail thử"); its query `notification-settings` is not polled.
- `hooks/`: TanStack Query hooks; UI components never call `api/` directly.
- `pages/`, `components/`. `components/ui/` is generated by Shadcn; avoid hand-editing it.
- Routing (`docs/sdd-landing-flow.md`):
  - `/` is the landing page for anonymous users; logged-in users are redirected to `/trips`.
  - `ProtectedRoute` sends logged-out users to `/login?returnTo=…`, except right after the user clicks **Đăng xuất** (`AuthProvider.logout()` sets `loggedOut`), when it sends them to `/`. A 401 uses `signOut()` and keeps the login redirect. `PublicOnlyRoute` sends logged-in users on to `returnTo`.
  - `/join/:code` is public. Anonymous users get "Tạo tài khoản & tham gia" / "Tôi đã có tài khoản" with `returnTo=/join/:code?auto=1`; `auto=1` joins once automatically after auth (the backend join is idempotent). `InviteHint` shows the trip name on login/register. Invite codes are parsed by `lib/inviteCode.ts` (plain code, `/join/…` or `/share/…` links).
  - Landing contact opens Zalo/Gmail (`VITE_CONTACT_ZALO`, `VITE_CONTACT_EMAIL` in `lib/config.ts`); there is no backend form. The `og:image` of `index.html` is `%OG_ORIGIN%/og-image.jpg`, which the `ogOrigin` Vite plugin fills from `VITE_SHARE_BASE_URL` at build time.
- Trip covers are either an http(s) URL or `preset:<key>`, which `lib/covers.ts` renders as a gradient. The backend validates both forms.
- Image upload: `ImageUploadButton` → `useUploadImage` → `lib/imageCompress.ts` (resizes on the client to at most 1920px and encodes WebP, or JPEG on Safari) → `api/media.ts`. That call must override `Content-Type: multipart/form-data`; otherwise axios turns the FormData into JSON.
- Query keys live in `tripKeys` (`hooks/useTrips.ts`). The availability and days keys sit **under** `detail(tripId)`, so invalidating a trip's detail refreshes them too. The availability PUT returns the full matrix, which is written straight into the cache.
- `useAvailabilityEditor` applies changes optimistically, debounces them by 600 ms, and sends them one request at a time. `AvailabilityGrid` lets you paint across cells by releasing pointer capture on `pointerdown` (needed on touch screens) and setting `touch-none` on your own row.
- Itinerary drag and drop uses `@dnd-kit`: Pointer, Touch (150 ms delay) and Keyboard sensors, a drag handle, and a DragOverlay. Collision detection checks day pills first (`pointerWithin`), then falls back to `closestCenter`. Dropping on another day's pill calls `move`; dropping within the list calls `reorder` with an optimistic update. dnd ids are built in `components/itinerary/dndIds.ts`.
- No realtime: `lib/queryClient.ts` polls every active query every 15 s while the browser tab is visible (`staleTime` 5 s, refetch on focus), so other members' changes show up without F5. Static queries opt out with `refetchInterval: false`. A mutation whose result is written into the cache should `cancelQueries` in `onMutate` so an in-flight poll can't overwrite it. The new-expense form stores *excluded* members, so people who join while it is open are included automatically.
- `setDetail` in `useTripCacheSync` invalidates **every** child query under `detail(tripId)`, so locking or unlocking refreshes availability, days, itinerary and checklist.
